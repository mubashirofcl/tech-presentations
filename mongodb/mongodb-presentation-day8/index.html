Full-Text Search

What Is Full-Text Search?

Full-text search allows us to search words inside text fields using an inverted word index.

🔍 How It Works

When searching for a word like "javascript", possible matching documents include:

  • JavaScript Complete Guide
  • Learn JavaScript
  • Advanced JavaScript Programming

Instead of scanning every character of every document manually, MongoDB builds a specialized text index that maps words directly to document locations.

🧠 The Mental Model: Book Index

Think of a textbook's back index:

"javascript" → Pages: 12, 45, 98, 140
"database" → Pages: 3, 22, 67
"pagination" → Pages: 88, 89, 90

You don't read the whole book from page 1 to find "javascript". You jump straight to the listed pages. That is what full-text search provides!

Full-Text Search

Why Not Use Normal Find?

Standard equality queries test the entire field value, which fails when users search for keywords.

find-exact.js
// Standard equality find db.products.find({ name: "iphone" })
❌ Exact Match Limitation

This query only matches if the name is strictly "iphone". If the product is named "Apple iPhone 15 Pro", this query returns NOTHING!

🛒 What Users Actually Expect

When an online shopper types "iphone", they expect to discover:

  • ✓ iPhone 15
  • ✓ Apple iPhone 15 Pro
  • ✓ iPhone 14 Case
  • ✓ Refurbished iPhone SE
The Solution

For word-based text searching across fields, MongoDB provides text indexes and the $text query operator.

Full-Text Search

Create a Text Index

Before executing a $text search, MongoDB requires a text index on the target fields.

1️⃣ Single-Field Text Index
single-text-index.js
db.products.createIndex({ name: "text" })

Now any words in the name field can be searched with $text.

2️⃣ Multi-Field Compound Text Index
multi-text-index.js
db.products.createIndex({ name: "text", description: "text" })

Searches will check both name and description simultaneously!

⚠️ Rule of MongoDB Text Indexes

A collection can have at most ONE text index. To search multiple fields, combine them into a single multi-field text index as shown above.

Full-Text Search

Searching Multiple Words

Passing multiple whitespace-separated terms performs an OR match across search words.

multi-word-search.js
db.products.find({ $text: { $search: "iphone case" } })
💡 Default Logical OR Behavior

By default, "iphone case" will find documents containing "iphone" OR "case".

Documents containing both terms are automatically ranked higher in relevance score!

🚀 Exact Phrase & Exclusion Modifiers

You can fine-tune text search using quotation marks and minus signs:

Exact Phrase Match (Wrap in escaped quotes):
$search: "\"iphone case\""
Matches only when "iphone case" appears consecutively.
Term Exclusion (Prefix with -):
$search: "iphone -pro"
Matches documents with "iphone" but excludes any with "pro".
Full-Text Search

Text Search vs Exact Search

Understanding the technical distinction between full-text, exact equality, and character matching.

Search Requirement Example Input Technique How It Matches
Exact Match "iPhone 15" { name: "iPhone 15" } Entire string must equal the query exactly.
Full-Text Search "iphone" $text: { $search: "iphone" } Matches independent complete words using an inverted text index.
Partial Character "iph" $regex: "iph", $options: "i" Matches substring anywhere inside text without word boundaries.
Autocomplete "iph..." Atlas Search autocomplete N-gram tokenized index designed for search-as-you-type keystrokes.
⚠️ Vital Teaching Note

$text is word-oriented, not a general substring search! If you search "iph" using $text, it will NOT match "iPhone" because "iph" is not a recognized whole word. For partial character matching, use $regex or Atlas Search autocomplete.

Search Relevance

What Is textScore?

When multiple documents match a text search, we need a way to rank the most relevant results first.

📊 Relevance Measurement

MongoDB calculates a numeric relevance score for every matched document called:

textScore

Factors that increase a document's textScore:

  • The frequency of search words in the document.
  • Whether the words match the title vs description.
  • How many different searched words are present.

Search Relevance

Getting textScore in Projection

Using the $meta: "textScore" projection operator to expose the calculated relevance score.

project-score.js
db.products.find( { $text: { $search: "iphone" } }, { score: { $meta: "textScore" } } )
Projection Syntax

The second argument in find() is the projection document. { score: { $meta: "textScore" } } adds a synthetic field named score to the output.

📋 Sample Returned Document
output.json
{ _id: ObjectId("66f123450001"), name: "iPhone 15 Pro", description: "Premium Apple smartphone", score: 1.5714285714285714 }

Notice the score field! By default, MongoDB returns results in natural insertion order. In the next slide, we will sort by this score to prioritize the best matches.

Search Relevance

Sorting by textScore

Ensuring the most relevant documents appear at the very top of search results.

sort-score.js
db.products.find( { $text: { $search: "iphone" } }, { score: { $meta: "textScore" } } ).sort({ score: { $meta: "textScore" } })
⚠️ Important Syntax Note

When sorting by textScore, you do not write 1 or -1. You write { score: { $meta: "textScore" } }. MongoDB automatically sorts from highest score to lowest score.

Partial Search

What Is Partial Search?

Sometimes users don't type the complete word or only remember a fragment of a name.

⌨️ User Types 3 Letters: "iph"

The user has not completed typing "iphone", but we want to return:

  • iPhone 15
  • iPhone 15 Pro
  • iPhone 14

Because "iph" is not an isolated dictionary word, $text search will return nothing. We need pattern/substring matching!

🧩 Substrings vs Complete Words
Full String: "Apple iPhone 15 Pro"
Search Substring: "iph"
Match found: Characters 7 to 9!

MongoDB provides the $regex operator to evaluate regular expression substring patterns directly against string fields.

Partial Search

Basic $regex Operator

Pattern matching with the $options: "i" flag for case-insensitivity.

regex-search.js
db.products.find({ name: { $regex: "iph", $options: "i" } })
🔤 What $options: "i" Does

The "i" option specifies case-insensitivity. This means:

iph IPH Iph

All three casings will successfully match!

🎮 Interactive Demo 3 — $regex Partial Search Live Filter
db.products.find({ name: { $regex: "iph", $options: "i" } })
Partial Search

Common Regex Patterns

Anchoring searches to the beginning, ending, or interior of string fields.

^ Starts With

The ^ anchor matches from the start:

{ name: { $regex: "^iph", $options: "i" } }

Matches: "iPhone 15"
Does NOT match: "Apple iPhone"

$ Ends With

The $ anchor matches at the end:

{ name: { $regex: "phone$", $options: "i" } }

Matches: "Smart Phone"
Does NOT match: "Phone Case"

* Contains Anywhere

No anchors — matches anywhere:

{ name: { $regex: "phone", $options: "i" } }

Matches: "iPhone", "Phone Case", "Earphone"

💡 Indexing Note for Starts-With:

A regex pattern with a prefix anchor like "^iph" can utilize standard B-Tree indexes on name! However, a contains search (no anchor) cannot use the index efficiently.

Partial Search

Practical $regex Example

Searching with a 3-letter prefix "lap" to discover laptop-related gear.

💻 The Search Query
search-lap.js
db.products.find({ name: { $regex: "lap", $options: "i" } })

This query scans strings to see if the character sequence "lap" appears in any casing.

📦 Possible Results Returned
  • Laptop (starts with "Lap")
  • Gaming Laptop (contains "Laptop")
  • Laptop Stand (starts with "Laptop")
  • Laptop Bag (starts with "Laptop")
Summary Rule

Use $regex when you need character-by-character substring matching where words may be incomplete or concatenated.

Performance Warning

$regex Performance Warning

Unanchored regular expressions can trigger expensive full-collection table scans.

⚠️ The Dangerous Query
{ name: { $regex: "phone" // No ^ anchor! } }

Because the pattern can match anywhere in the string, MongoDB cannot use an index prefix to jump directly to candidates. It must inspect every single document in the collection!

🚨 Collection Scan (COLLSCAN)

On a collection of 500,000 products, this query will evaluate the regex 500,000 times, causing CPU spikes, high disk I/O, and query timeouts.

🛡️ Best Practices for Regex in Production
  • Anchor with ^ whenever possible: { name: { $regex: "^iphone" } } allows MongoDB to perform an indexed range scan.
  • Combine with indexed filters: Filter by category or userId first, then run regex on the small subset.
  • Always limit results: Always chain .limit(20) so MongoDB stops scanning once enough records are found.
  • Upgrade to Atlas Search: For true search-as-you-type at scale, use Atlas Search instead of regex.

Database Indexing

What Is an Index?

A specialized data structure (B-Tree) that holds a sorted copy of selected fields to accelerate queries.

📚 The Library Analogy

Imagine finding a book in a library with 100,000 volumes:

Without Index (COLLSCAN): Walk through every aisle, reading every book cover one by one until you find it. (Exhausting & slow!)
With Index (IXSCAN): Consult the sorted card catalog, read the shelf number, and walk directly to the book in 2 seconds!

Simple Index Example

Creating a single-field index on frequently queried fields like email or username.

1️⃣ The Target Query

If the students collection has 200,000 records, this query scans 200,000 documents by default.

2️⃣ Create the Index

Now MongoDB constructs a sorted B-Tree index on email. Future lookups complete in O(log N) steps!

Database Indexing

Index Direction: 1 vs -1

Understanding ascending (1) and descending (-1) sort order in B-Tree index keys.

⬆️ Ascending: { age: 1 }

Values are ordered from smallest to largest:

18 → 19 → 20 → 21 → 22 → 25 → 30
⬇️ Descending: { age: -1 }

Values are ordered from largest to smallest:

30 → 25 → 22 → 21 → 20 → 19 → 18
⚠️ Essential Classroom Clarification

For single-field equality lookups, direction does not matter! MongoDB can traverse a single-field B-tree in either direction with equal speed. Direction only becomes crucial when building compound indexes that support multi-field sorting (e.g. sort by course ASC and mark DESC).

Database Indexing

Common Index Types

The primary index types every MongoDB developer must know.

1️⃣ Single Field
{ email: 1 }

Indexes a single top-level field for equality and range filters.

2️⃣ Compound Index
{ course: 1, mark: -1 }

Indexes multiple fields together for compound queries and multi-field sorting.

3️⃣ Multikey Index
{ skills: 1 }

Automatically created when indexing an array field (e.g. skills: ["JS", "MongoDB"]).

4️⃣ Text Index
{ name: "text" }

Builds an inverted word index for the $text search operator.

5️⃣ Unique Index
{ email: 1 }, { unique: true }

Rejects duplicate values, enforcing uniqueness at the database engine level.

6️⃣ Default _id Index
{ _id: 1 }

Created automatically on every MongoDB collection. Cannot be deleted.

Database Indexing

Compound Indexes

Indexing multiple fields together to support combined filtering and sorting patterns.

compound-index.js
// Create compound index db.students.createIndex({ course: 1, mark: -1 })
🎯 Perfect Query Match
db.students.find({ course: "MERN" }).sort({ mark: -1 })

MongoDB filters by course: "MERN" and returns documents in sorted mark order directly from the index without an in-memory sort!

📐 The ESR Rule (Equality, Sort, Range)

When designing compound indexes, order your fields using the ESR rule:

1. Equality (E)
course: "MERN"
↓
2. Sort (S)
mark: -1
↓
3. Range (R)
age: { $gte: 18 }

Following ESR guarantees that MongoDB narrows candidates before sorting, maximizing query throughput.

Performance Trade-offs

Too Many Indexes?

Indexes improve read speeds, but they carry significant maintenance and write costs.

📉 The Costs of Every Index
  • RAM & Storage Footprint: Every index must fit in wiredTiger cache (RAM). Large indexes evict active data pages.
  • Write Overhead: On every insert, update, or delete, MongoDB must synchronously update every index on the collection.
  • Index Maintenance: B-Tree node splitting and rebalancing consumes CPU cycles during heavy write bursts.

More indexes ≠ Always better! Audit unused indexes periodically using $indexStats.

Pagination

Understanding limit()

Restricting the maximum number of documents returned by a query cursor.

limit-example.js
db.products .find() .limit(10)
🎯 Behavior

Returns at most 10 documents.

If the collection only has 4 documents, it returns 4. If it has 50,000 documents, it stops after 10.

⚡ Database Efficiency

When you attach .limit(10), MongoDB stops reading as soon as the 10th document is reached. The database engine does not waste resources fetching the remaining records.

Next Step:

limit() gives us page size. But how do we reach Page 2 or Page 3? That is where skip() comes in!

Pagination

Page-Based Pagination Formula

The standard mathematical formula used in Express and Node.js APIs to calculate offset.

🧮 The Formula
const limit = 10; const skip = (page - 1) * limit;
Page 1 → skip = (1 - 1) * 10 = 0
Page 2 → skip = (2 - 1) * 10 = 10
Page 3 → skip = (3 - 1) * 10 = 20

Mongoose Pagination in Express

Implementing a production-grade GET /products?page=2&limit=10 endpoint.

productController.js
const getProducts = async (req, res) => { const page = Number(req.query.page) || 1; const limit = Number(req.query.limit) || 10; const skip = (page - 1) * limit; const products = await Product.find() .sort({ createdAt: -1 }) .skip(skip) .limit(limit); const total = await Product.countDocuments(); res.json({ products, page, limit, total, totalPages: Math.ceil(total / limit) }); };
🌐 API Response Schema
200 OK Response
{ "page": 2, "limit": 10, "total": 150, "totalPages": 15, "products": [ { "_id": "66f1...", "name": "Product 11" } ] }
⚠️ Always Use a Stable Sort

Never call skip() without .sort()! Without an explicit sort order, document order is non-deterministic and records may duplicate across pages.

Performance Bottleneck

The Problem With Large skip()

Why offset pagination deteriorates as users or bots request deep page numbers.

💥 The Deep Page Scenario
Page = 1,000
Limit = 20
skip = (1,000 - 1) × 20 = 19,980

To fulfill skip(19980).limit(20), MongoDB cannot teleport to row 19,980. It still has to traverse past all 19,980 documents and discard them before returning the 20 requested records!

📈 Performance Latency Curve
Page 1 (skip: 0)~1 ms
Page 50 (skip: 1,000)~15 ms
Page 500 (skip: 10,000)~180 ms
Page 2,500 (skip: 50,000)~1,200 ms (Lag!)
The Flaw:

Offset pagination scale is O(N) where N is the offset. We need an O(1) solution: Cursor Pagination!

Cursor Pagination

Better Approach: Cursor Pagination

Instead of counting offsets, we query for records sequentially after a known pointer.

❌ The Offset Mindset (skip)

"Please skip 19,980 documents, then give me the next 20."

Forces the database to step through 19,980 records in index or memory before finding what you want.

✅ The Cursor Mindset (range)

"Give me 20 documents whose _id is greater than the last document I saw."

The B-Tree index jumps directly to that exact key in O(log N) steps and reads 20 documents. Zero documents are skipped!

Also Known As:

Cursor-based pagination is also called Range-based pagination, Keyset pagination, or Token pagination.

Cursor Pagination

Cursor Pagination API Example

How frontend and backend exchange cursor tokens across sequential requests.

1️⃣ First Request (Page 1)
GET /products?limit=10
Response
{ products: [ ...10 items... ], nextCursor: "66f123450010", hasMore: true }
2️⃣ Subsequent Request (Page 2)
GET /products?limit=10&cursor=66f123450010
Response
{ products: [ ...next 10 items... ], nextCursor: "66f123450020", hasMore: true }
The Magic of nextCursor

The client simply passes the nextCursor back in the query string. The database uses it to resume immediately from that spot.

Cursor Pagination

Cursor Query Concept ($gt)

Under the hood, MongoDB uses an indexed range query: _id: { $gt: lastId }.

cursor-query.js
// When cursor is provided: db.products.find({ _id: { $gt: lastId } }) .sort({ _id: 1 }) .limit(10)
⚡ Why ObjectId Works Naturally

MongoDB's default _id is a 12-byte ObjectId containing an embedded 4-byte creation timestamp. Because ObjectIds naturally increment over time, sorting by _id: 1 automatically orders by insertion date!

Comparison

Offset vs Cursor Pagination

A side-by-side decision matrix to choose the right pagination architecture.

Feature skip() + limit() (Offset) Cursor Pagination ($gt)
Implementation Complexity ✓ Simple Easy math: (page - 1) * limit Medium Requires tracking cursor tokens
Jump to Arbitrary Page (Page 50) ✓ Yes Directly calculate offset ✗ No Can only navigate sequentially
Deep Page Performance ✗ Degrades (O(N)) Scans & discards records ✓ Constant (O(1)) Instant indexed jump
Infinite Scroll Feeds ✗ Risky Page shifts if new docs are inserted ✓ Perfect Immune to item insertion shifts
Large Datasets (1M+ Docs) ✗ Less Suitable High memory and query latency ✓ Highly Scalable Industry standard
Display Total Page Numbers ✓ Supported Page [ 1 ] [ 2 ] [ 3 ] Usually "Load More"
When to use skip + limit:

Internal admin dashboards, small collections (< 10,000 docs), or tables requiring explicit page numbers.

When to use Cursor pagination:

Social feeds, mobile infinite scroll, public developer APIs, and high-throughput real-time collections.

Practical Project

Search Endpoint: Implementation

Switching dynamically between $text and $regex based on input length.

searchProducts.js
const buildSearchQuery = (q) => { if (!q) return {}; // If query is at least 3 chars, use full-text search if (q.trim().length >= 3) { return { $text: { $search: q } }; } // For short inputs (e.g. "ph"), use partial regex return { name: { $regex: q, $options: "i" } }; };
🧠 Why This Hybrid Strategy Works
  • Complete Words: Queries like q=phone or q=shoes leverage the fast inverted text index with textScore.
  • Partial Typing: Very short queries like q=pho gracefully fall back to $regex without erroring out.
  • Safeguard: By restricting regex to short inputs and always adding .limit(), collection scan penalties remain controlled.

Pagination API: Implementation

export const getProducts = async (req, res) => { const page = Math.max(1, parseInt(req.query.page, 10) || 1); const limit = Math.min(50, Math.max(1, parseInt(req.query.limit, 10) || 10)); const skip = (page - 1) * limit; const filter = buildSearchQuery(req.query.q); // Run query and total count in parallel for maximum speed const [products, total] = await Promise.all([ Product.find(filter).sort({ createdAt: -1 }).skip(skip).limit(limit), Product.countDocuments(filter) ]); res.json({ products, page, limit, total, totalPages: Math.ceil(total / limit) }); };

Practical Indexes for Project

Creating exactly the indexes required by our project queries — and knowing why each exists.

1️⃣ Text Search Index
db.products.createIndex({ name: "text", description: "text" })

Why it exists: Powers all $text: { $search: ... } queries across product titles and details.

2️⃣ Category Index
db.products.createIndex({ category: 1 })

Why it exists: Users frequently filter by department (e.g. category: "Footwear").

3️⃣ Price Sort Index
db.products.createIndex({ price: 1 })

Why it exists: Allows sorting products by "Price: Low to High" without in-memory sort penalty.

💡 The Indexing Takeaway

Notice how every single index corresponds to a specific user filter or sort! We didn't index stock or internal timestamps because queries don't filter on them.

Anti-Patterns

Common Mistakes to Avoid

The 8 most frequent mistakes made by junior developers when implementing search & pagination.

1

Expecting $text to Be Substring Search

Searching "iph" with $text will return 0 results because $text searches whole word tokens, not character substrings.

2

Using $regex Everywhere on Large Collections

Unanchored regex (e.g. /phone/) triggers full collection scans, spiking CPU and crashing production databases.

3

Creating Indexes on Every Single Field

More indexes ≠ faster database. Every index slows down insert, update, and delete operations and consumes RAM.

4

Returning the Entire Collection Without limit()

Calling Product.find() without limits sends thousands of documents across the wire, exhausting memory and crashing frontends.

5

Using Very Large skip() Values for Deep Pages

skip(50000) still iterates past 50,000 documents. For deep feeds or infinite scroll, always use cursor pagination.

6

Forgetting a Stable Sort Order During Pagination

Paginating without an explicit .sort() produces non-deterministic order, causing duplicate or missing records across pages.

7

Assuming Atlas Autocomplete Works Without Search Index

The $search stage will throw an error if an Atlas Search index with an autocomplete analyzer is not created first.

8

Ignoring .explain("executionStats")

Never guess whether a query is fast. Run .explain() to verify whether MongoDB used an index (IXSCAN) or scanned all docs (COLLSCAN).
