Core Concepts

What Is a User Session?

How servers remember a user's login state across multiple stateless HTTP requests.

Slide 02

The Stateless HTTP Problem

By default, HTTP is a stateless protocol. This means the server treats every single request as completely independent. Once the response is sent, the server forgets who made the request!

Without Sessions: If a student logs in, navigates to their profile page, and then clicks on their grades, the server would ask them to log in again on every single click!

The Solution: A session is a server-side data structure created upon login. It gives the client a temporary identity card (session ID cookie) so the server instantly recognizes the user on future requests.

Real-World Analogy: The Event Wristband

When you buy a ticket at an amusement park or concert:

  • • You present your ID and ticket at the gate (Login).
  • • The gatekeeper straps a numbered wristband to your wrist (Session ID Cookie).
  • • Whenever you enter a ride, security glances at your wristband rather than asking for your full ticket and ID every single time (Protected Requests)!

Web Protocols & Security

What Are Cookies & How Do They Work?

The browser's automatic credential carrier and essential security flags.

Slide 04

How Cookies Work in HTTP

A cookie is a small piece of data (key-value pair) sent by the server in the HTTP response using the Set-Cookie header.

HTTP Response Header
Set-Cookie: student.sid=s%3Aabc123...; Path=/; HttpOnly; SameSite=Lax

Once stored, the browser automatically attaches this cookie to every future HTTP request to the same domain via the Cookie: header:

Cookie: student.sid=s%3Aabc123...

Critical Cookie Security Properties

Property Security Purpose & Protection
httpOnly: true Blocks JavaScript from reading document.cookie. Stops XSS attacks!
secure: true Cookie is only transmitted over HTTPS. Stops packet sniffing!
sameSite: "lax" Controls cross-origin transmission. Stops CSRF attacks!
maxAge: 3600000 Sets cookie expiration in ms (e.g. 1 hour). Prevents zombie sessions.
Crucial Security Truth: The session ID stored in the cookie is never the user's password or database record. It is merely an unforgeable, cryptographically signed reference key.

Phase A: Login & Session Creation

  1. 1. Student submits login credentials via HTTPS POST.
  2. 2. Express checks the database and validates the password using bcrypt.compare().
  3. 3. Server creates a new session in MongoDB and saves req.session.userId = user.id.
  4. 4. Server returns HTTP 200 with the header: Set-Cookie: student.sid=<signed_id>; HttpOnly.

Phase B: Authenticating Protected Routes

  1. 5. Browser accesses GET /profile and automatically includes the cookie.
  2. 6. Session middleware reads the cookie, verifies the signature, and fetches session data from MongoDB.
  3. 7. authMiddleware inspects req.session.userId. If present, calls next()!
  4. 8. The controller sends back the student profile!
Express Middleware

What Is express-session?

The standard Express middleware for creating, signing, reading, and destroying user sessions.

Slide 06
Basic express-session Setup
// 1. Install via npm: npm install express-session
const express = require("express");
const session = require("express-session");

const app = express();

// 2. Configure session middleware
app.use(
  session({
    secret: "my-secret-key-12345", // Signs the session ID cookie
    resave: false,                // Don't resave if unmodified
    saveUninitialized: false       // Don't save empty sessions
  })
);

Configuration Options Explained

  • • secret: Secret key used by the server to cryptographically sign the cookie. This guarantees that an attacker cannot alter their session ID in the browser.
  • • resave: false: Prevents saving the session back to the database on every request if nothing in req.session was modified. Dramatically reduces DB load!
  • • saveUninitialized: false: Ensures unauthenticated visitors don't create empty session documents in MongoDB, keeping your database clean.
CRITICAL WARNING: The MemoryStore Trap
By default, express-session uses an in-memory store. In production, memory stores leak memory, don't scale across multiple servers, and erase every active user on server restart! Always use a database store like connect-mongo!

Practical: Create Your First Session

Build a visit counter route and observe how the session cookie persists across requests.

Slide 07
visit-demo.js
const express = require("express");
const session = require("express-session");

const app = express();

app.use(
  session({
    secret: "student-session-secret",
    resave: false,
    saveUninitialized: true
  })
);

// GET /visit — Increments session counter
app.get("/visit", (req, res) => {
  req.session.visits = (req.session.visits || 0) + 1;

  res.json({
    message: "Session example",
    visits: req.session.visits
  });
});

app.listen(3000, () => console.log("Running on port 3000"));

Production Architecture

Practical: Configure Session Middleware with MongoDB

Connect express-session to MongoDB using connect-mongo for durable storage.

Slide 09
server.js (Session Configuration)
require("dotenv").config();
const express = require("express");
const session = require("express-session");
const MongoStore = require("connect-mongo");

const app = express();
app.use(express.json());

app.use(
  session({
    name: "student.sid",
    secret: process.env.SESSION_SECRET,
    resave: false,
    saveUninitialized: false,

    // Store sessions in MongoDB
    store: MongoStore.create({
      mongoUrl: process.env.MONGO_URI,
      collectionName: "sessions",
      ttl: 60 * 60 * 24 // 1 day in seconds
    }),

    cookie: {
      httpOnly: true,
      secure: process.env.NODE_ENV === "production",
      sameSite: "lax",
      maxAge: 1000 * 60 * 60 // 1 hour in ms
    }
  })
);

Production Configuration Breakdown

Property Explanation & Security Impact
name Custom cookie name (student.sid) masks framework fingerprint.
MongoStore Persists session documents in MongoDB collection named sessions.
ttl Time To Live in MongoDB. Automatically deletes expired sessions via TTL index.
cookie.httpOnly Protects session ID from client-side JavaScript access (Anti-XSS).
cookie.secure Enforces HTTPS in production; permits HTTP in local development.
Database Prerequisite: Ensure MongoDB is running locally at mongodb://127.0.0.1:27017 or via MongoDB Atlas before starting the Express server!
Session State Management

How to Store User Information in a Session

Understand what belongs inside server session storage vs. what stays in browser cookies.

Slide 10

The Server-Client Split

When a student logs in, we attach minimal identifying data to req.session:

// Inside login route handler:
req.session.userId = user.id;
req.session.email = user.email;
SERVER SESSION (MongoDB)
{ userId: 101, email: "john@gmail.com" }
↔
BROWSER COOKIE
student.sid = s%3Aabc123...

What to Store vs. What to Exclude

NEVER STORE PASSWORDS: Even though session data resides on the server, storing passwords (even hashed ones) inside session documents creates unnecessary security risks!
  • ✓ DO STORE: The primary key identifier (e.g. userId) and user role (role: "student").
  • × DON'T STORE: Entire user profile objects, large blobs of data, or credit card numbers. Keep sessions lean and lightning fast!
  • ✓ Cryptographic Tamper Proofing: The cookie contains a HMAC signature of the session ID signed with SESSION_SECRET. If an attacker modifies the cookie value, Express immediately rejects it!
Hands-on Implementation

Practical: User Registration Endpoint

Accept student registration data, hash passwords using bcryptjs, and store safely.

Slide 11
server.js (Registration Route)
const bcrypt = require("bcryptjs");

// In-memory users array for demonstration
const users = [];

// POST /register
app.post("/register", async (req, res) => {
  try {
    const { name, email, password } = req.body;

    // 1. Check if email already registered
    const existingUser = users.find(u => u.email === email);
    if (existingUser) {
      return res.status(409).json({ message: "User already exists" });
    }

    // 2. Hash password with 10 salt rounds
    const hashedPassword = await bcrypt.hash(password, 10);

    // 3. Create user record
    const user = {
      id: Date.now(),
      name,
      email,
      password: hashedPassword
    };
    users.push(user);

    // 4. Return 201 Created
    res.status(201).json({ message: "Registration successful" });
  } catch (error) {
    res.status(500).json({ message: "Registration failed" });
  }
});

Registration Lifecycle Steps

  1. 1. Extract Inputs: Pull name, email, and password from req.body.
  2. 2. Duplicate Prevention (409): Ensure no two students share the same email address.
  3. 3. One-Way Cryptographic Hashing: Convert plain text passwords into salt-reinforced bcrypt strings.
  4. 4. Store Record: Push user object into storage. In Day 9, this array will be replaced by a Mongoose schema!
Expected Output (201 Created): 
{
  "message": "Registration successful"
}
Hands-on Implementation

Practical: User Login & Session Creation

Verify passwords, regenerate session IDs to prevent fixation, and issue the session cookie.

Slide 12
server.js (Login Route)
// POST /login
app.post("/login", async (req, res, next) => {
  try {
    const { email, password } = req.body;

    // 1. Locate student by email
    const user = users.find(u => u.email === email);
    if (!user) {
      return res.status(401).json({ message: "Invalid email or password" });
    }

    // 2. Verify password with bcrypt
    const isMatch = await bcrypt.compare(password, user.password);
    if (!isMatch) {
      return res.status(401).json({ message: "Invalid email or password" });
    }

    // 3. Regenerate session ID (Anti-Fixation)
    req.session.regenerate(error => {
      if (error) return next(error);

      // 4. Store user ID in session
      req.session.userId = user.id;

      // 5. Persist to MongoDB session store
      req.session.save(err => {
        if (err) return next(err);
        res.json({ message: "Login successful" });
      });
    });
  } catch (err) {
    next(err);
  }
});

Why Use req.session.regenerate()?

Session Fixation Attack Defense: In a session fixation attack, a malicious actor gives a victim a known session ID (e.g. through a phishing link). If the server continues using that same session ID after the victim logs in, the attacker gains full unauthorized access!
  • ✓ req.session.regenerate() wipes the old anonymous session ID and produces a completely fresh, random session ID upon successful login.
  • ✓ req.session.save() ensures the session document is committed to MongoDB before the HTTP response headers (and Set-Cookie) are sent.

What Is Authentication Middleware?

The gatekeeper pattern: Inspecting req.session.userId before granting route access.

How the Gatekeeper Works

In Express, middleware functions execute sequentially. By inserting authMiddleware between the route path and your controller, unauthorized visitors are blocked before your controller even executes.

  • • If req.session.userId exists → Session is active → calls next().
  • • If req.session.userId is missing → No active session → returns 401 immediately.

Reusability across 50+ Routes

You write authMiddleware.js once, and you can attach it to protect any number of routes across your application:

app.get("/profile", authMiddleware, profileController);
app.get("/grades", authMiddleware, gradesController);
app.post("/submit-quiz", authMiddleware, quizController);
Hands-on Implementation

Practical: Creating authMiddleware.js

Build the reusable session validation middleware in its own modular file.

Slide 14
middleware/authMiddleware.js
// Session Authentication Guard
function authMiddleware(req, res, next) {
  // 1. Check if session exists and has userId
  if (!req.session || !req.session.userId) {
    return res.status(401).json({
      success: false,
      message: "Please login first"
    });
  }

  // 2. Valid active session found -> proceed!
  next();
}

module.exports = authMiddleware;

Code Walkthrough & Error Handling

Condition Server Response
No cookie sent 401 Unauthorized ("Please login first")
Cookie tampered or expired 401 Unauthorized ("Please login first")
Session deleted (logged out) 401 Unauthorized ("Please login first")
Valid active session Calls next() to run controller
Notice: The middleware does not need to send custom database queries manually. express-session and connect-mongo already populated req.session automatically before this middleware runs!
Hands-on Implementation

Practical: Create Protected Profile Route

Attach authMiddleware to GET /profile and retrieve user data using req.session.userId.

Slide 15
server.js (Protected Route)
const authMiddleware = require("./middleware/authMiddleware");

// GET /profile — PROTECTED ROUTE
app.get("/profile", authMiddleware, (req, res) => {
  // 1. Retrieve user using ID stored in session
  const user = users.find(u => u.id === req.session.userId);

  if (!user) {
    return res.status(401).json({ message: "User not found" });
  }

  // 2. Return student profile (omit password!)
  res.json({
    message: "Welcome to your profile",
    user: {
      id: user.id,
      name: user.name,
      email: user.email
    }
  });
});

How the Request Is Authenticated

  1. 1. When the student navigates to /profile, the browser sends Cookie: student.sid=....
  2. 2. express-session reads the session document from MongoDB and attaches it to req.session.
  3. 3. authMiddleware verifies that req.session.userId is present and calls next().
  4. 4. The route handler looks up the student record and sends the profile response.

Session Destruction

Practical: Logout & Destroy Session

Destroy server-side MongoDB session documents and clear browser cookies.

Slide 16
server.js (Logout Route)
// POST /logout
app.post("/logout", (req, res, next) => {
  // 1. Destroy session in MongoDB session store
  req.session.destroy(error => {
    if (error) {
      return next(error);
    }

    // 2. Clear browser cookie
    res.clearCookie("student.sid", {
      path: "/"
    });

    // 3. Return confirmation
    res.json({
      message: "Logout successful"
    });
  });
});

The Complete Logout Pipeline

Step 1
User Clicks Logout → Client calls POST /logout
↓
Step 2
Destroy Server Session → Deleted from MongoDB
↓
Step 3
Clear Browser Cookie → res.clearCookie("student.sid")
Instant Invalidation: Once req.session.destroy() finishes, any subsequent request to GET /profile fails with 401 Unauthorized!
