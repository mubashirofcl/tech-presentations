Core Concepts

What Is Authentication?

Understanding identity verification vs. access permission in modern web applications.

Slide 03

1. Authentication (AuthN)

The Core Question: "Who are you?"

The process of verifying that an entity (user or service) is genuinely who they claim to be by validating supplied credentials.

Real-World Analogy: Showing your official Student Identity Card or Passport at the campus security gate to prove your identity.
  • ✓ Email & Password verification
  • ✓ Multi-Factor Authentication (OTP, SMS)
  • ✓ Biometric login (FaceID, Fingerprint)

2. Authorization (AuthZ)

The Core Question: "What are you allowed to do?"

The process of determining whether an authenticated user has the necessary permissions to access a specific resource or perform an action.

Real-World Analogy: Your Student ID proves who you are (AuthN), but it doesn't give you access to the Professor's Faculty Lounge (AuthZ)!
  • ✓ Role-Based Access Control (Admin vs. Student)
  • ✓ Can user edit this grade? Can user delete this post?
  • ✓ Executed after authentication succeeds.
Dimension Authentication (AuthN) Authorization (AuthZ)
Purpose Validates user identity Validates permissions & privileges
Mechanisms Passwords, OTPs, Biometrics, SSO Roles (Admin, User), Scopes, Permissions
HTTP Status on Failure 401 Unauthorized (Not logged in) 403 Forbidden (Logged in, but denied)

Traditional Session vs. Modern JWT

  • • Session-Based (Stateful): The server stores session data in RAM or Redis. For millions of users, servers require massive memory synchronization across clusters.
  • • JWT-Based (Stateless): The server does NOT store sessions in memory. The token itself contains all necessary claims. Any backend server with the secret key can verify it instantly!

Why Stateless Tokens Win for MERN & Microservices

Stateless tokens allow seamless horizontal scaling. Whether your request hits Server A, Server B, or Server C behind a load balancer, each server can verify the cryptographic signature independently without shared database lookups.

Stateless Rule: "The server doesn't remember who you are. The client presents a cryptographic passport on every request."
Security Fundamentals

Why Should We Hash Passwords?

Never store plain text passwords. Learn the mathematics of one-way cryptographic hashing.

Slide 05

The Danger of Plain Text Passwords

If an attacker accesses your database through SQL/NoSQL injection, backup leaks, or compromised developer credentials, all user passwords are compromised immediately.

Catastrophic Impact: Because 65%+ of users reuse passwords across multiple sites, a leak on your student portal compromises their personal email, banking, and social accounts!

What Is Cryptographic Hashing?

Hashing is a one-way mathematical function that transforms input text of any length into a unique, fixed-length string.

  • ✓ Irreversible: It is computationally impossible to reverse the hash back into the plain text password.
  • ✓ Deterministic: The exact same input always generates the exact same hash output.

What Is a Cryptographic "Salt"?

A salt is a unique, random string of bytes generated and appended to the password before hashing. Even if two students choose the exact same password (password123), their generated hashes will be completely different! This completely neutralizes pre-computed Rainbow Table attacks.

Why bcrypt over MD5 or SHA-256?

MD5 and SHA-256 were designed for speed; a modern GPU can compute billions of SHA-256 hashes per second. bcrypt is deliberately slow and includes an adjustable cost factor (work factor), making brute-force attacks infeasible.

// 1. Import bcryptjs
const bcrypt = require('bcryptjs');

async function demonstrateBcrypt() {
  const plainPassword = 'student123';
  const saltRounds = 10; // 2^10 iterations

  // 2. Hash the password
  const hashedPassword = await bcrypt.hash(plainPassword, saltRounds);
  console.log('Hashed Password:', hashedPassword);

  // 3. Verify on Login
  const isMatch = await bcrypt.compare(plainPassword, hashedPassword);
  console.log('Password Match:', isMatch); // true

  // 4. Test with wrong password
  const isWrong = await bcrypt.compare('wrongPass', hashedPassword);
  console.log('Wrong Match:', isWrong); // false
}

Token Deep-Dive

What Is JSON Web Token (JWT)?

RFC 7519 open standard: A compact, URL-safe, self-contained method for securely transmitting claims.

Slide 07
A Real Encoded JWT Token (Separated by dots)
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VySWQiOiJzdGRfMTAxIiwicm9sZSI6InN0dWRlbnQiLCJlbWFpbCI6ImFsZXhAY29sbGVnZS5lZHUifQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
1. Header (Red) Specifies token type and signing algorithm (e.g. HS256). 
{
  "alg": "HS256",
  "typ": "JWT"
}
2. Payload (Purple) Contains the claims: user ID, role, expiration timestamp. 
{
  "userId": "std_101",
  "role": "student"
}
3. Signature (Cyan) HMAC SHA-256 hash using the header, payload & server secret. 
HMACSHA256(
  base64Url(header) + "." +
  base64Url(payload),
  secretKey
)
CRITICAL SECURITY NOTE: Base64Url is ENCODED, NOT ENCRYPTED! Anyone with the token can decode and read the payload. NEVER store passwords, API keys, or credit card details inside a JWT payload!
What Prevents Tampering? The Signature! If an attacker changes "role": "student" to "admin", the cryptographic signature won't match, and the server rejects it with 401 Unauthorized.
Protocol Flow

How JWT Authentication Works (Step-by-Step)

The complete HTTP conversation between client browser and Express server.

Slide 08

Phase A: Login & Token Issuance

  1. 1. Client POST: Browser sends POST /api/login with { email, password }.
  2. 2. Backend Verification: Server looks up user and verifies password hash using bcrypt.compare().
  3. 3. Sign Token: Server creates a JWT containing { userId, role } signed with process.env.JWT_SECRET.
  4. 4. Client Response: Server sends back HTTP 200 with { token: "eyJhbGciOi..." }.
  5. 5. Storage: Client application stores token in memory or local storage.

Phase B: Accessing Protected Endpoints

  1. 6. Client GET: Browser sends request to GET /api/profile with header:
    Authorization: Bearer eyJhbGciOi...
  2. 7. Middleware Intercept: authMiddleware parses the header and extracts the token.
  3. 8. Cryptographic Check: Server runs jwt.verify(token, secret). If valid, attaches payload to req.user and calls next().
  4. 9. Response: Controller executes and returns student profile data!
Standard Convention: The Authorization header uses the standard format Bearer <token>. "Bearer" signifies that whoever bears this token is granted access.

Practical: Generate a JWT with jwt.sign()

Install jsonwebtoken and construct signed cryptographic tokens with expiration.

generate-token.js 
// 1. Import jsonwebtoken library
const jwt = require('jsonwebtoken');
require('dotenv').config();

// 2. Define user payload (public claims)
const payload = {
  userId: 'std_101',
  email: 'alex@college.edu',
  role: 'student'
};

// 3. Secret key loaded from .env
const secretKey = process.env.JWT_SECRET || 'mySuperSecretKey_2026';

// 4. Sign token with expiration (1 hour)
const token = jwt.sign(payload, secretKey, {
  expiresIn: '1h' // '15m', '2h', '7d'
});

console.log('Generated JWT Token:\n', token);

secretKey String Private key stored in .env used to sign and verify.
options Object Options like { expiresIn: '1h' } to auto-expire tokens.

Token Deep-Dive

Understanding JWT Verification

How jwt.verify() detects tampering, validates expiration, and extracts claims.

Slide 10
verify-token.js 
const jwt = require('jsonwebtoken');
const secretKey = 'mySuperSecretKey_2026';

// Validating an incoming token
function validateToken(token) {
  try {
    // Verifies signature and expiration
    const decoded = jwt.verify(token, secretKey);
    console.log('Token Valid! Decoded payload:', decoded);
    return { valid: true, decoded };
  } catch (error) {
    // jwt.verify throws error if invalid or expired
    if (error.name === 'TokenExpiredError') {
      console.error('Token has expired!');
    } else {
      console.error('Invalid token signature!', error.message);
    }
    return { valid: false, error: error.message };
  }
}

What Happens During jwt.verify()?

  1. 1. Signature Re-computation: Takes Header and Payload from the token and recalculates HMAC SHA-256 with the server's secret.
  2. 2. Cryptographic Match: Compares computed signature with the token's signature. If even 1 bit was altered, verification fails immediately!
  3. 3. Timestamp Check: Checks current Unix timestamp against exp (expiration) and iat (issued at). If expired, throws TokenExpiredError.
Common Error Types:
  • JsonWebTokenError: invalid signature → Secret didn't match or token tampered.
  • TokenExpiredError: jwt expired → Token lifetime exceeded.

Hands-on Implementation

Practical: User Registration API

Implement POST /api/register with duplicate checks, password hashing, and clean HTTP 201 responses.

Slide 12
routes/authRoutes.js (Register) 
const express = require('express');
const bcrypt = require('bcryptjs');
const router = express.Router();

// In-memory student database array
const students = [];

// POST /api/register
router.post('/register', async (req, res) => {
  try {
    const { name, email, password } = req.body;

    // 1. Validation
    if (!name || !email || !password) {
      return res.status(400).json({ error: 'All fields are required' });
    }

    // 2. Check if student already exists
    const existingStudent = students.find(s => s.email === email);
    if (existingStudent) {
      return res.status(409).json({ error: 'Email already registered' });
    }

    // 3. Hash the plain password with salt
    const hashedPassword = await bcrypt.hash(password, 10);

    // 4. Save new student
    const newStudent = {
      id: String(students.length + 101),
      name,
      email,
      password: hashedPassword
    };
    students.push(newStudent);

    // 5. Return 201 Created (NEVER return password!)
    res.status(201).json({
      message: 'Student registered successfully',
      student: { id: newStudent.id, name, email }
    });
  } catch (err) {
    res.status(500).json({ error: 'Server registration error' });
  }
});

Registration Logic Breakdown

  • ✓ Input Validation (400): Verify name, email, and password are present.
  • ✓ Duplicate Prevention (409): Use students.find() to check if the email already exists in the system. 409 Conflict is the correct REST status.
  • ✓ One-Way Hashing: bcrypt.hash(password, 10) ensures plain text never enters storage.
  • ✓ Data Sanitization: The JSON response returns the student's ID, name, and email—never the hashed password!
Expected Output (201 Created): 
{
  "message": "Student registered successfully",
  "student": {
    "id": "101",
    "name": "Sarah Connor",
    "email": "sarah@college.edu"
  }
}

Practical: User Login API

Implement POST /api/login with bcrypt comparison, token signing, and security best practices.

Slide 13
routes/authRoutes.js (Login) 
const jwt = require('jsonwebtoken');

// POST /api/login
router.post('/login', async (req, res) => {
  try {
    const { email, password } = req.body;

    // 1. Find student by email
    const student = students.find(s => s.email === email);
    if (!student) {
      return res.status(401).json({ error: 'Invalid email or password' });
    }

    // 2. Compare entered password with stored hash
    const isMatch = await bcrypt.compare(password, student.password);
    if (!isMatch) {
      return res.status(401).json({ error: 'Invalid email or password' });
    }

    // 3. Generate signed JWT token
    const token = jwt.sign(
      { userId: student.id, email: student.email, role: 'student' },
      process.env.JWT_SECRET,
      { expiresIn: '1h' }
    );

    // 4. Send token back to client (200 OK)
    res.status(200).json({
      message: 'Login successful',
      token
    });
  } catch (err) {
    res.status(500).json({ error: 'Server login error' });
  }
});

Security Best Practices for Login

Prevent User Enumeration Attacks: Notice that whether the email doesn't exist OR the password is wrong, we return the exact same message: "Invalid email or password". Never tell attackers "Email not found"!
Expected Output (200 OK): 
{
  "message": "Login successful",
  "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VySWQiOi..."
}

Client Next Steps:

The client stores this token. For all subsequent requests to protected endpoints, the client attaches this token in the HTTP Authorization header.

Middleware Pattern

What Is Authentication Middleware?

The gatekeeper pattern: Protecting Express routes before they reach your controller logic.

Slide 14
Step 1
HTTP Request
Incoming GET /profile with Bearer Token
→
Step 2: Gatekeeper
authMiddleware
Extracts header, runs jwt.verify(), sets req.user
→
Step 3
Route Controller
Runs business logic safely with req.user data
→
Step 4
JSON Response
200 OK + Student Profile Payload

Responsibilities of authMiddleware

  • • Inspect incoming req.headers.authorization header.
  • • Check if header exists and starts with "Bearer ".
  • • Split string to isolate the raw JWT token.
  • • Verify cryptographic signature against process.env.JWT_SECRET.
  • • If valid: Attach payload to req.user and call next().
  • • If invalid or missing: Immediately abort with 401 Unauthorized!

Why Use Middleware Instead of Repeating Code?

In a large application with 50+ protected routes (e.g. /profile, /grades, /submit-assignment, /enroll), copying and pasting token verification into every controller would create maintenance nightmares.

DRY (Don't Repeat Yourself): By writing authMiddleware once, you can protect any Express route simply by inserting it into the route definition:
router.get('/profile', authMiddleware, profileController);
Hands-on Implementation

Practical: Creating authMiddleware.js

Build the complete, production-grade token extraction and verification middleware.

Slide 15
middleware/authMiddleware.js 
const jwt = require('jsonwebtoken');

const authMiddleware = (req, res, next) => {
  // 1. Read the Authorization header
  const authHeader = req.headers.authorization;

  // 2. Verify header existence and format
  if (!authHeader || !authHeader.startsWith('Bearer ')) {
    return res.status(401).json({
      error: 'Access denied. No token provided.'
    });
  }

  // 3. Extract the token (split by space)
  const token = authHeader.split(' ')[1];

  try {
    // 4. Verify signature using secret key
    const decoded = jwt.verify(token, process.env.JWT_SECRET);

    // 5. Attach decoded payload to request
    req.user = decoded;

    // 6. Pass control to the next handler
    next();
  } catch (err) {
    return res.status(401).json({
      error: 'Invalid or expired token.'
    });
  }
};

module.exports = authMiddleware;

Code Walkthrough & Error Paths

Scenario Condition Checked Action
No Header !authHeader Returns 401 immediately.
Bad Prefix !startsWith('Bearer ') Returns 401 immediately.
Tampered Token jwt.verify() throws Caught in catch; returns 401.
Valid Token jwt.verify() succeeds Sets req.user & calls next().
Why req.user = decoded? By attaching the decoded payload to the Express req object, downstream controllers can read the user's ID (e.g. req.user.userId) without having to re-decode or re-verify the token!

Practical: Creating Protected Routes

Attach authMiddleware to GET /api/profile and access verified user context from req.user.

Slide 16
routes/authRoutes.js (Protected Route) 
const express = require('express');
const router = express.Router();
const authMiddleware = require('../middleware/authMiddleware');

// GET /api/profile — PROTECTED ROUTE
router.get('/profile', authMiddleware, (req, res) => {
  // req.user was populated by authMiddleware!
  const authenticatedUserId = req.user.userId;

  // Find student in database
  const student = students.find(s => s.id === authenticatedUserId);

  if (!student) {
    return res.status(404).json({ error: 'Student profile not found' });
  }

  // Return profile data safely
  res.status(200).json({
    success: true,
    student: {
      id: student.id,
      name: student.name,
      email: student.email,
      role: req.user.role
    }
  });
});

module.exports = router;

Full Express Server Integration

server.js 
const express = require('express');
require('dotenv').config();

const app = express();
app.use(express.json());

// Mount authentication routes
const authRoutes = require('./routes/authRoutes');
app.use('/api', authRoutes);

const PORT = process.env.PORT || 5000;
app.listen(PORT, () => {
  console.log(`Auth server running on port ${PORT}`);
});
