Part 1: Structured Output

The Problem with Unstructured LLM Text

Why natural language breaks backend applications, and how JSON solves it

FOUNDATIONS
⚠️ The Freeform Output Problem

Ask an LLM to extract student details: "Rahul is 22 years old. He is learning MERN Stack. Email: rahul@gmail.com."

Sample Output:
The student's name is Rahul. He is 22 years old and learning MERN Stack. His email is rahul@gmail.com.
Node.js Access Result:
❌ student.name => undefined ❌ student.age => undefined Result is unstructured prose. Requires fragile regex to parse.
✨ The Solution: Structured JSON

Generating JSON from an LLM

Guiding the model to emit machine-readable text without conversational fluff

PROMPT TO JSON
generateJson.js
const response = await groq.chat.completions.create({
  model: "llama-3.3-70b-versatile",
  messages: [
    {
      role: "system",
      content: `Extract student details from message.
Return ONLY valid JSON with keys: name, age, course, email.
No markdown backticks. No conversational text.`
    },
    {
      role: "user",
      content: "Rahul is 22. Email: rahul@gmail.com. Course: MERN Stack."
    }
  ],
  temperature: 0.2
});

const rawText = response.choices[0].message.content;
const student = JSON.parse(rawText);
console.log(student.name); // "Rahul"
⚠️ The Golden Rule of AI JSON

Prompts guide intent, but cannot guarantee valid data.

  • ✗ Models can wrap output in ```json ... ``` markdown fences.
  • ✗ Models can output conversational preamble ("Sure, here is your JSON:").
  • ✗ Models can hallucinate missing fields or output invalid data types (age: "twenty-two").
The Engineering Implication:

Prompt instructions reduce failure rates, but server-side runtime validation is non-negotiable before touching databases or business logic!

Structural Contracts

What Is JSON Schema?

The standard IETF specification for declaring expected data shapes

SPECIFICATION
student.schema.json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "type": "object",
  "properties": {
    "name": { "type": "string" },
    "age": { "type": "integer", "minimum": 16, "maximum": 60 },
    "course": { "type": "string" },
    "email": { "type": "string", "format": "email" }
  },
  "required": ["name", "age", "course", "email"],
  "additionalProperties": false
}
🔑 Core JSON Schema Keywords
KeywordFunction
typeSpecifies primitive type (string, integer, etc.)
propertiesDeclares permitted object keys and nested rules
requiredArray of keys that MUST be present
additionalPropertiesWhen false, rejects unexpected extra keys
Describing vs Validating:

JSON Schema describes structure. It doesn't validate data in Node.js on its own—that's where Zod comes in!

Schema Construction

Defining Rich Zod Schemas

Chained validation rules, enums, arrays, and modifier methods

ZOD METHODS
richStudentSchema.js
const { z } = require("zod");

const studentSchema = z.object({
  name: z.string().min(2),
  age: z.number().int().min(16).max(60),
  email: z.string().email(),
  course: z.enum(["MERN Stack", "Python", "Data Science"]),
  skills: z.array(z.string()),

  // Real-world modifiers:
  phone: z.string().optional(),        // Allows undefined
  notes: z.string().nullable(),        // Allows null
  status: z.string().default("active") // Fallback value
});
📚 Method Cheat Sheet
MethodRule Enforced
.int()Rejects decimal numbers (e.g. 22.5)
.min(2)String must be at least 2 characters
.email()Valid RFC 5322 email address format
z.enum([...])Must strictly match one of allowed strings
z.array(...)Must be an array of specified types
.transform(fn)Mutates data during parse (e.g. .trim())
optional() vs nullable(): .optional() permits undefined. .nullable() permits null. If an LLM returns null, use .nullish() to allow both!

Error Formatting

Handling Validation Errors

Inspecting result.error.issues to provide actionable feedback

ZOD ISSUES
🔍 Anatomy of a Zod Issue

When validation fails, Zod produces an array of descriptive issue objects:

issuesSample.json
[
  {
    "code": "invalid_type",
    "expected": "number",
    "received": "string",
    "path": ["age"],
    "message": "Expected number, received string"
  }
]
🛠️ User-Friendly Error Formatting

Transform raw issues into a clean dictionary for REST responses or retry prompts:

formatIssues.js
function formatZodErrors(error) {
  const formatted = {};
  error.issues.forEach(issue => {
    const field = issue.path.join(".");
    formatted[field] = issue.message;
  });
  return formatted;
}

// Returns: { age: "Expected number, received string" }
GenAI Self-Correction Loop: If an LLM hallucinates an invalid field, pass these exact error messages into a follow-up prompt so the model can auto-correct itself!
Pipeline Synthesis

Practical: Validating AI Structured Output

Combining Groq completions, JSON.parse, and Zod safeParse in a resilient script

AI VALIDATE
aiValidate.js
const response = await groq.chat.completions.create({
  model: "llama-3.3-70b-versatile",
  messages: [
    { role: "system", content: "Extract info and return valid JSON with: name, age, email, course." },
    { role: "user", content: "Rahul is 22 years old. Email: rahul@gmail.com. Learning MERN Stack." }
  ],
  temperature: 0.2
});

const aiText = response.choices[0].message.content;

try {
  // Step 1: Syntax Validation
  const parsed = JSON.parse(aiText);

  // Step 2: Schema & Type Validation
  const validation = studentSchema.safeParse(parsed);
  if (!validation.success) {
    console.log("AI Data Schema Errors:", validation.error.issues);
  } else {
    console.log("Safely Validated Student:", validation.data);
  }
} catch (syntaxErr) {
  console.log("JSON Syntax Error:", syntaxErr.message);
}
🛡️ The Two-Tier Shield
Tier 1: try / catch (JSON.parse)

Protects against malformed text, backticks, trailing commas, or markdown formatting.

Tier 2: safeParse(studentSchema)

Protects against missing keys, wrong data types, or out-of-range ages.

Execution Output:
Safely Validated Student: { name: 'Rahul', age: 22, email: 'rahul@gmail.com', course: 'MERN Stack' }
Part 3: Function Calling

From Structured Output to Function Calling

Moving from generating passive data to requesting backend actions

AGENTIC SHIFT
⚡ The Next Evolutionary Step

In Part 1, the LLM returned structured data based on what was in the prompt. But what if the data lives in a live database or requires an external API?

Function Calling (Tool Calling) allows the model to request that our Node.js server execute a real function (e.g. get_attendance(101)) and wait for the result!

⚠️ Critical Distinction:

The LLM does NOT execute code. It emits a tool request. Your Node.js backend maintains 100% control over execution and database permissions!

Secure Invocation

Tool Execution via Tool Registry Map

Dispatching functions through an explicit lookup table without dangerous eval()

REGISTRY MAP
toolRegistry.js
// 1. Ordinary JavaScript Functions
function getStudent(studentId) {
  return students.find(s => s.id === studentId) || null;
}

function getAttendance(studentId) {
  const student = getStudent(studentId);
  if (!student) return { error: "Student not found" };
  return { studentId, name: student.name, attendance: student.attendance };
}

// 2. Explicit Registry Map (Security Perimeter)
const availableTools = {
  get_student: getStudent,
  get_attendance: getAttendance
};

// 3. Safe Lookup and Execution
const toolFn = availableTools[toolCall.function.name];
if (!toolFn) throw new Error("Unknown tool");

const result = toolFn(validated.data.studentId);
🔒 Security Architecture Rule

Never use eval() or execute arbitrary dynamic function names sent by the model.

The tool registry dictionary guarantees that only explicitly whitelisted functions in your application can ever be invoked.

Database Independence: Notice how getStudent can query in-memory arrays today, and be swapped with db.students.findOne() tomorrow without altering the AI orchestration!

Defensive Coding

Error Handling in Tool Calling

Gracefully catching unknown tools, bad arguments, and record misses

RESILIENCE
safeExecuteTool.js
function executeTool(toolCall) {
  const toolName = toolCall.function.name;
  try {
    const tool = availableTools[toolName];
    const schema = argumentSchemas[toolName];
    if (!tool || !schema) throw new Error("Unknown tool");

    const args = JSON.parse(toolCall.function.arguments);
    const validated = schema.safeParse(args);
    if (!validated.success) throw new Error("Invalid tool arguments");

    return tool(validated.data.studentId);
  } catch (error) {
    // Return error payload instead of crashing server!
    return { error: true, message: error.message };
  }
}
⚠️ Failure Modes Caught
  • ✗ Unknown Tool: Hallucinated tool name safely rejected.
  • ✗ Bad JSON: Malformed arguments handled gracefully.
  • ✗ Invalid Types: Negative or string IDs blocked by Zod.
  • ✗ Record Not Found: Missing student returns null.
When an error object is returned as tool output, the LLM will politely inform the user: "I could not find student 999 in our records."

The complete executeTool, runAssistant, and POST /chat Express endpoint

CAPSTONE PART 2
ai-student-assistant/server.js (Part 2)
function executeTool(toolCall) {
  const toolName = toolCall.function.name;
  try {
    const tool = availableTools[toolName];
    const schema = argumentSchemas[toolName];
    if (!tool || !schema) throw new Error("Unknown tool");

    const args = JSON.parse(toolCall.function.arguments);
    const validated = schema.safeParse(args);
    if (!validated.success) throw new Error("Invalid tool arguments");

    return tool(validated.data.studentId);
  } catch (error) {
    return { error: true, message: error.message };
  }
}

async function runAssistant(question) {
  const messages = [
    { role: "system", content: "You are an AI Student Assistant. Use tools to answer questions. Do not invent facts." },
    { role: "user", content: question }
  ];

  const res1 = await groq.chat.completions.create({
    model: MODEL, messages, tools, tool_choice: "auto"
  });

  const msg = res1.choices[0].message;
  if (!msg.tool_calls?.length) return msg.content;

  messages.push(msg);
  for (const toolCall of msg.tool_calls) {
    const result = executeTool(toolCall);
    messages.push({
      role: "tool", tool_call_id: toolCall.id,
      name: toolCall.function.name, content: JSON.stringify(result)
    });
  }

  const finalRes = await groq.chat.completions.create({
    model: MODEL, messages, tools, tool_choice: "none"
  });
  return finalRes.choices[0].message.content;
}

app.post("/chat", async (req, res) => {
  const { question } = req.body;
  if (!question) return res.status(400).json({ error: "Question required" });
  const answer = await runAssistant(question);
  res.json({ success: true, answer });
});

app.listen(3000, () => console.log("Assistant on port 3000"));
