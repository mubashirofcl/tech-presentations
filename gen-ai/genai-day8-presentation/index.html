Core Concepts

What Is Function Calling?

Bridging the gap between static text generation and dynamic software execution

CONCEPT
📖 Definition & Purpose

Function Calling (Tool Calling) is an architectural technique that allows an LLM to request the execution of a specific function inside our Node.js application.

Normally, an LLM only predicts words based on training data. With function calling, it can request our application to perform real-world tasks:

  • ✓
    Retrieve student details from a database
  • ✓
    Check real-time attendance percentages
  • ✓
    Calculate accurate totals without math hallucinations
  • ✓
    Query internal SQL / MongoDB databases
  • ✓
    Call external REST APIs (weather, payments, email)
💡 Concrete Scenario
User Asks:
"What is the attendance percentage of student 101?"
Application Bridge:
1. LLM requests: getStudentAttendance({ studentId: 101 })
↓
2. Node.js executes: db.query(101) ➔ returns 85%
↓
3. LLM replies: "Arun's attendance is 85%."
⚠️ Critical Security Fact:

The LLM does NOT directly execute our JavaScript function. It only outputs a structured request containing the tool name and arguments. Your Node.js backend decides whether and how to execute it!

📋 Detailed Step Breakdown
  1. User Query: User asks a question (e.g. "Who is student 101?").
  2. Tool Schemas: Node.js sends the question + available tool schemas to Groq.
  3. Tool Selection: The LLM decides a tool is needed, pauses generation, and returns the tool name & arguments.
  4. Node.js Execution: Node.js validates arguments with Zod and executes the local JavaScript function.
  5. Final Synthesis: Node.js sends tool results back to Groq; the model generates a friendly final answer.
⚖️ Responsibility Division

Validating argument data types Node.js (Zod)
Connecting to DB / running function Node.js Backend
Explaining result in plain English LLM (Groq)
Components of a Tool

What Is a Tool?

A backend capability made available to an LLM through three essential parts

TOOL ANATOMY
🧩 The Three Parts of a Tool
  • 1. Tool Definition (Schema):
    The JSON Schema describing what the tool does, its parameters, and required arguments to the model.
  • 2. Tool Implementation (Function):
    The real, ordinary JavaScript function inside your Node.js application that does the work.
  • 3. Tool Execution (Orchestrator):
    The glue code that matches the LLM's requested tool name, validates arguments, calls the function, and returns the result.
Tool Name Purpose
getStudentDetailsFetch student name & course by ID
getAttendanceFetch student attendance percentage
calculateTotalCompute fees or invoice sums
💻 Ordinary JavaScript Implementation

Notice that the function itself knows nothing about AI or LLMs—it is standard Node.js:

studentFunctions.js 
function getStudentDetails(studentId) {
  const students = [
    { id: 101, name: "Arun", course: "MERN" },
    { id: 102, name: "Rahul", course: "Python" }
  ];

  return students.find(student => student.id === studentId) || null;
}

// Testing plain JavaScript execution:
console.log(getStudentDetails(101));
Direct Execution Output:
{ id: 101, name: 'Arun', course: 'MERN' }

What Is a Tool Schema?

Teaching the model what functions exist and how to call them

TOOL DEFINITION
tools.js (Groq-Compatible Tool Schema) 
const tools = [
  {
    type: "function",
    function: {
      name: "get_student",
      description: "Get student details using student ID",
      parameters: {
        type: "object",
        properties: {
          studentId: {
            type: "number",
            description: "The unique student ID"
          }

        required: ["studentId"]

    }
  }

The description is the prompt! The model reads this description to decide if the tool matches the user's intent. Clear descriptions prevent tool misuse.

JSON Schema tells the LLM the structure to produce. But the LLM produces a text string. Node.js still requires an active runtime validator (Zod) to ensure the data is safe.

Argument Extraction

What Are Tool Arguments?

Understanding how the model packages and returns parameter values

ARGUMENTS PARSING
📦 Tool Arguments Are Stringified JSON

When an LLM requests a tool, it passes the required parameters as a JSON-encoded string:

tool-call-snippet.json
{
  "name": "get_student",
  "arguments": "{\"studentId\":101}"
}

Notice that arguments is NOT a JavaScript object yet—it is escaped stringified text. We must deserialize it with JSON.parse().

⚙️ Node.js Parsing Example
parseArguments.js 
const argumentsString = '{"studentId":101}';

// Step 1: Parse the JSON string into an object
const args = JSON.parse(argumentsString);

// Step 2: Access extracted properties
console.log(args.studentId); // 101
Terminal Output:
101
⚠️ Safety Warning: Never blindly execute functions with raw parsed arguments! What if the model outputs { "studentId": "DROP TABLE" } or -999? Always validate with Zod first.
Argument Guardrails

What Is Zod and Why Do We Need It?

Runtime validation to protect backend functions against bad AI arguments

ZOD VALIDATION
🛡️ Why Argument Validation Is Crucial

An LLM can occasionally return unexpected types: { studentId: "hello" } when your function expects an integer. Zod prevents crashes.

terminal
npm install zod
zodValidation.js
const { z } = require("zod");

const studentSchema = z.object({
  studentId: z.number().int().positive()
});

// Test 1: Valid argument
const res1 = studentSchema.safeParse({ studentId: 101 });
console.log(res1.success); // true

// Test 2: Invalid argument string
const res2 = studentSchema.safeParse({ studentId: "hello" });
console.log(res2.success); // false

Groq API Integration

Practical: Sending Tools to Groq

Configuring the Groq SDK client and passing tool schemas in chat completions

GROQ COMPLETION
groq-tools-demo.js 
require("dotenv").config();
const Groq = require("groq-sdk");

const groq = new Groq({ apiKey: process.env.GROQ_API_KEY });
const MODEL = "openai/gpt-oss-120b";

async function askAssistant() {
  const response = await groq.chat.completions.create({
    model: MODEL,
    messages: [
      { role: "user", content: "Who is student 101?" }
    ],
    tools: tools,
    tool_choice: "auto"
  });

  // The response may contain a tool call instead of normal text!
  console.log(response.choices[0].message);
}

askAssistant();
🔍 Critical Observations
  • Model: Uses openai/gpt-oss-120b, an open-weight enterprise model optimized for tool use on Groq.
  • Passing Tools: The tools array is passed directly into chat.completions.create.
  • No Execution Yet: Groq returns an intention/request. Your server must inspect the response to see if a tool call was issued!
Groq Ecosystem Note: Groq supports native tool calling with ultra-low latency, making multi-turn function calling fast enough for real-time applications.

Execution Engine

How to Execute a Tool in Node.js

Connecting the LLM's requested tool name to actual JavaScript functions via a tool map

TOOL REGISTRY
toolExecution.js 
// Step 1: Real JavaScript functions
function getStudent(studentId) {
  const students = [
    { id: 101, name: "Arun", course: "MERN" },
    { id: 102, name: "Rahul", course: "Python" }
  ];
  return students.find(s => s.id === studentId) || null;
}

// Step 2: Tool Registry Map (Crucial security boundary!)
const availableTools = {
  get_student: getStudent
};

// Step 3: Execute safely by lookup
const toolName = "get_student";
const args = { studentId: 101 };

const result = availableTools[toolName](args.studentId);
console.log(result);

Completing the Handshake

Tool Result: Sending Data Back to the LLM

Appending role: "tool" messages to conversation history for final answer synthesis

TOOL ROLE
🔁 Constructing the Tool Result Message

After your JavaScript function runs, format its output as a tool role message:

appendToolResult.js
// 1. Push assistant's tool-call request
messages.push(assistantMessage);

// 2. Push tool result with matching tool_call_id
messages.push({
  role: "tool",
  tool_call_id: toolCall.id,
  name: "get_student",
  content: JSON.stringify(result)
});

// 3. Request final conversational answer
const finalResponse = await groq.chat.completions.create({
  model: MODEL,
  messages: messages,
  tools: tools,
  tool_choice: "none"
});
🔑 Why tool_call_id Is Crucial

The tool_call_id binds the result to the specific invocation requested by the model. This is especially vital when an LLM requests multiple tools in parallel.

Final Synthesized Answer:
"Student 101 is Arun. He is enrolled in the MERN Stack course."
tool_choice: "none" in Step 3

Setting tool_choice: "none" guarantees the model will not loop or request another tool; it immediately synthesizes the final human response.

Defensive Engineering

Tool Execution: Error Handling

Gracefully handling invalid arguments, missing records, and unknown tool requests

RESILIENCE
⚠️ Four Common Failure Modes
  • ✗
    Unknown Tool: Model requests a hallucinated tool name.
  • ✗
    Malformed JSON: Argument string fails JSON.parse().
  • ✗
    Invalid Types: Negative ID or string passed to number parameter.
  • ✗
    Record Not Found: Query for student ID 999 returns null.
safeExecute.js
function executeTool(toolName, args) {
  try {
    const tool = availableTools[toolName];
    if (!tool) throw new Error("Unknown tool");
    return tool(args.studentId);
  } catch (error) {
    return { error: true, message: error.message };
  }
}

Implementation Part 2

Practical Code: Tool Execution & Express API

The complete executeTool, runAssistant, and POST /chat implementation

SERVER.JS PART 2
ai-student-assistant/server.js (Part 2) 
// Safe Tool Execution Helper
function executeTool(toolCall) {
  const toolName = toolCall.function.name;
  try {
    const tool = availableTools[toolName];
    const schema = argumentSchemas[toolName];
    if (!tool || !schema) throw new Error("Unknown tool");

    const args = JSON.parse(toolCall.function.arguments);
    const validated = schema.safeParse(args);
    if (!validated.success) throw new Error("Invalid tool arguments");

    return tool(validated.data.studentId);
  } catch (error) {
    return { error: true, message: error.message };
  }
}

// Orchestration Engine
async function runAssistant(question) {
  const messages = [
    { role: "system", content: "You are an AI Student Assistant. Use available tools to answer questions. Do not invent facts." },
    { role: "user", content: question }
  ];

  // Request 1: Let LLM decide whether to use tools
  const response = await groq.chat.completions.create({
    model: MODEL, messages, tools, tool_choice: "auto"
  });

  const assistantMessage = response.choices[0].message;
  if (!assistantMessage.tool_calls?.length) {
    return assistantMessage.content;
  }

  messages.push(assistantMessage);

  // Execute each tool call
  for (const toolCall of assistantMessage.tool_calls) {
    const result = executeTool(toolCall);
    messages.push({
      role: "tool",
      tool_call_id: toolCall.id,
      name: toolCall.function.name,
      content: JSON.stringify(result)
    });
  }

  // Request 2: Final synthesis
  const finalResponse = await groq.chat.completions.create({
    model: MODEL, messages, tools, tool_choice: "none"
  });

  return finalResponse.choices[0].message.content;
}

// Express Endpoint
app.post("/chat", async (req, res) => {
  try {
    const { question } = req.body;
    if (typeof question !== "string" || !question.trim()) {
      return res.status(400).json({ error: "Question is required" });
    }
    const answer = await runAssistant(question);
    res.json({ success: true, answer });
  } catch (err) {
    res.status(500).json({ success: false, message: "Something went wrong" });
  }
});

app.listen(process.env.PORT || 3000, () => console.log("Assistant running"));
