Introduction to Agent Workflows

Intermediate AI/LLM – Day 2: Dividing Complex Goals into Reliable Multi-Step Systems

DAY 2 • WORKFLOWS
🧭 What are Agent Workflows?

An Agent Workflow is an architectural pattern that divides a complex objective into distinct, coordinated steps executed by specialized prompts, functions, or agents. Rather than relying on a single unpredictable LLM prompt to solve everything, workflows bring software engineering discipline to AI systems.

1. Sequential Flow Pipeline where output of step A becomes input to step B. Predictable and strictly ordered.
2. Parallel Flow Concurrent execution of independent tasks using Promise.all() to slash total response latency.
3. Router Pattern Classification gate directing user queries to the optimal specialized prompt or domain handler.
4. Human-in-the-Loop Mandatory approval checkpoints for financial, irreversible, or sensitive actions before execution.
🏢 Real-World Example: Enterprise Leave Agent

Consider an employee asking: "Please check my leave balance and submit 3 days of leave starting next Monday."

1
Extract Parameters: Parse dates, count, and reason.
2
Database Check: Query HR database for remaining PTO balance.
3
Calendar Validation: Confirm dates don't clash with team blackout periods.
4
Manager Gate: If > 2 days, route to manager for approval.

Why Do We Need Agent Workflows?

The Limits of Single Prompts vs The Power of Structured Multi-Step Pipelines

WORKFLOW ADVANTAGES
⚠️ The Failure of "Do Everything" Single Prompts

Asking an LLM in one monolithic prompt to: "Read this 20-page document, verify 5 accounting constraints, calculate taxes, update database records, and draft an executive email" inevitably leads to critical failures:

  • ✗ Attention Degradation: LLMs skip subtle business constraints buried in complex prompts.
  • ✗ Zero Deterministic Guarantees: Mathematical calculations and DB operations can hallucinate.
  • ✗ Impossible Debugging: When a single mega-prompt produces a bad result, you cannot isolate which step failed.
  • ✗ All-or-Nothing Latency: If one sub-task fails, the entire prompt must be completely re-run.
🛡️ The 4 Pillars of Structured Workflows
1
Validation & Error Boundaries: Each step validates its own inputs and outputs before triggering subsequent actions.
2
Deterministic Logic Injection: Mix LLM reasoning for unstructured text with rigid Node.js code for math, permissions, and SQL.
3
Auditability & Observability: Log the exact output, token cost, and execution duration of every individual step.
4
Modular Iteration: Optimize or swap a prompt or model for Step 2 without breaking Steps 1, 3, or 4.
💡 Engineering Principle: In production AI, architecture beats prompt engineering. Breaking a 1-step prompt into a 3-step workflow routinely boosts reliability from 70% to > 98%.

Sequential Workflow (A → B → C)

Chaining Linear Operations Where Output N Feeds Directly Into Step N+1

SEQUENTIAL PATTERN
🔗 Architecture: Linear Chain of Responsibility

In a Sequential Workflow, tasks execute strictly one after another. Step B cannot start until Step A completes and passes its verified structured output.

Step 1 Understand Request LLM parses natural language into JSON dates & count
→
Step 2 Check HR Database Node.js checks employee leave balance > requested
→
Step 3 Validate Calendar Checks company holidays and project deadlines
→
Step 4 Submit & Notify Inserts record into HRIS & emails supervisor
✅ Best Suited For
  • • Multi-step form processing (Extract → Validate → Save).
  • • Code generation pipelines (Draft → Lint → Test → Commit).
  • • Summarization pipelines (Transcript → Outline → Executive Summary).
⚠️ Key Consideration: Cascade Latency

Because steps are synchronous, the total execution time is the cumulative sum:

Total Time = Time(A) + Time(B) + Time(C) + Time(D)

Practical: Sequential Workflow in Node.js

Executing Chained Async Steps with Error Boundaries in CommonJS

PRACTICAL • NODE.JS
sequentialWorkflow.js 
// sequentialLeaveWorkflow.js - CommonJS Implementation
const { parseLeaveWithLLM } = require('./llmParser');
const { getEmployeeBalance, saveLeaveRecord } = require('./db');

async function processLeaveWorkflow(employeeId, userPrompt) {
  try {
    // Step 1: LLM extracts structured intent
    const request = await parseLeaveWithLLM(userPrompt);
    console.log(`[Step 1] Parsed: ${request.days} days starting ${request.startDate}`);

    // Step 2: Deterministic Database Check
    const balance = await getEmployeeBalance(employeeId);
    if (balance < request.days) {
      return { success: false, error: `Insufficient balance: ${balance} days remaining.` };
    }
    console.log(`[Step 2] Balance verified: ${balance} days available.`);

    // Step 3: Date Validation
    if (new Date(request.startDate) < new Date()) {
      return { success: false, error: 'Start date cannot be in the past.' };
    }

    // Step 4: Final Database Record Insertion
    const record = await saveLeaveRecord({ employeeId, ...request });
    return { success: true, leaveId: record.id, message: 'Leave submitted successfully!' };
  } catch (err) {
    return { success: false, error: err.message };
  }
}

module.exports = { processLeaveWorkflow };
🔍 Code Walkthrough & Best Practices
  • 1. Early Exit Guard: If Step 2 fails (insufficient balance), we exit immediately without wasting time or tokens on Steps 3 and 4.
  • 2. Mixing LLM with Code: We use the LLM only for Step 1 (unstructured string parsing), and use strict JavaScript for Steps 2 and 3. Never let the LLM do math or permission checks!
  • 3. Standardized Output: Every return statement conforms to { success: boolean, ... }, allowing caller functions to handle responses reliably.
✓ Result: Fully deterministic execution with clear audit checkpoints.

Parallel Workflow

Fan-Out & Fan-In Architecture: Concurrently Executing Independent Tasks

PARALLEL PATTERN
⚡ The Need for Speed: Concurrency

Often, a system needs multiple independent analyses of the same document or input. Running them sequentially wastes precious seconds. In a Parallel Workflow, we "fan out" requests across multiple workers simultaneously, and "fan in" when all finish.

Incoming Support Ticket
↓ [Fan-Out via Promise.all()]
Worker 1
Sentiment Analysis (Positive, Neutral, Angry)
Worker 2
Topic Extraction (Billing, Bug, Inquiry)
Worker 3
Urgency Scoring (Low, Medium, Critical)
↓ [Fan-In Aggregation]
Aggregated Structured Ticket Object Ready for Dispatch
⏱️ Latency Comparison
S
Sequential Latency: 1.2s + 1.1s + 1.3s = 3.6 seconds. User waits noticeably.
P
Parallel Latency: max(1.2s, 1.1s, 1.3s) = ~1.3 seconds (> 60% faster!).
⚠️ API Rate Limits: Parallel requests hit the LLM provider concurrently. Ensure your API tier supports the required Requests Per Minute (RPM).

Practical: Promise.all() in Node.js

Executing Concurrent AI Workers with Structured Aggregation

PRACTICAL • PROMISE.ALL
parallelWorkflow.js 
// parallelTicketAnalysis.js - CommonJS Implementation
const { analyzeSentiment, extractTopic, scoreUrgency } = require('./analyzers');

async function processSupportTicketInParallel(ticketText) {
  const startTime = Date.now();

  // Launch all 3 independent LLM tasks simultaneously
  const [sentiment, topic, urgency] = await Promise.all([
    analyzeSentiment(ticketText),
    extractTopic(ticketText),
    scoreUrgency(ticketText)
  ]);

  const duration = Date.now() - startTime;
  console.log(`All parallel analyses completed in ${duration}ms`);

  return {
    processedAt: new Date().toISOString(),
    sentiment,   // e.g. "FRUSTRATED"
    topic,       // e.g. "BILLING_DISPUTE"
    urgency,     // e.g. "HIGH"
    executionTimeMs: duration
  };
}

module.exports = { processSupportTicketInParallel };
💡 Implementation Details
  • • Array Destructuring: const [sentiment, topic, urgency] = await Promise.all([...]) matches the exact index order of the promises passed in.
  • • Fail-Fast Behavior: Standard Promise.all() rejects immediately if any promise throws. If partial success is acceptable, use Promise.allSettled() instead.
  • • Benchmarking: Measuring duration helps verify the latency speedup during automated test suites.
📌 Key Rule: Only parallelize tasks that have zero dependencies on each other. If Task B requires Task A's result, use sequential chaining.

Sequential vs Parallel Workflow

Architectural Trade-offs & Selection Criteria

WORKFLOW COMPARISON
Dimension Sequential Workflow (Chained) Parallel Workflow (Concurrent)
Data Dependency Strict: Step N depends directly on Step N-1 None: All tasks run independently on the original input
Execution Latency Cumulative sum: Time(A) + Time(B) + Time(C) Bottleneck bounded: max(Time(A), Time(B), Time(C))
Error Blast Radius Early termination stops subsequent steps immediately One failure does not delay others (with allSettled)
API Rate Limit Impact Low: Requests are spaced out in time High: Sudden spike in concurrent API tokens/connections
Ideal Use Cases Multi-stage calculations, order checkout, database updates Multi-angle analysis, document translation to 5 languages, fact-checking
When to Choose Sequential

When correctness and validation must precede action. E.g., Do not call the credit card charge API until the inventory check confirms the item is in stock.

When to Choose Parallel

When synthesizing diverse perspectives or performing multi-category tagging where speed is top priority and tasks do not modify shared state.

Dynamic Request Dispatching to Specialized Handlers and Focused Prompts

ROUTER PATTERN
🔀 What is the Router Pattern?

Instead of burdening one giant system prompt with hundreds of rules for every possible topic, the Router Pattern acts as an intelligent dispatcher:

1
Classify: A lightweight classifier inspects user intent.
2
Dispatch: The router sends the query to a specialized agent.
3
Execute: The chosen agent responds with tailored domain tools.
✨ Token Savings: Specialized agents use 150-word prompts instead of a 3,000-word monolith. Faster, cheaper, and far more accurate!

Human-in-the-Loop (HITL)

Safeguarding High-Stakes Actions with Supervised Approval Gates

HITL SAFETY PATTERN
🛑 Why AI Needs Supervised Guardrails

While AI agents excel at drafting text, summarizing data, and retrieving information, irreversible real-world actions must never occur without human oversight:

  • 🚫 Financial Disbursements: Issuing refunds > $500 or corporate wire transfers.
  • 🚫 Data Deletion / DB Mutations: Dropping tables, wiping user accounts, or bulk edits.
  • 🚫 Legal & Medical Decisions: Executing legally binding contracts or patient prescriptions.
⚠️ The 80/20 Rule of HITL: Automate the 80% repetitive, low-risk requests; route the 20% high-risk, ambiguous exceptions to human managers.
🚦 Approval Threshold Architecture
Rule Gate: Expense > $500 Triggers suspension of execution and flags human supervisor.
1
Drafting: Agent prepares the action payload and validates fields.
2
State Persist: Saves status as PENDING_HUMAN_APPROVAL in DB.
3
Notification: Sends Slack message or email with Approve/Reject links.
4
Resume: Once approved, the workflow resumes execution.

Section 2 RAG Fundamentals

What is RAG?

Retrieval-Augmented Generation: Bridging Static LLMs with Private Enterprise Knowledge

RAG DEFINITION
📖 What Does RAG Mean?

RAG (Retrieval-Augmented Generation) is an architectural pattern that searches external knowledge sources (PDFs, docs, databases) for relevant information and injects that information directly into the LLM's prompt before generation.

R
Retrieval: Search your company's documents to find the most relevant paragraphs.
A
Augmentation: Combine the retrieved text + user question into an enriched prompt.
G
Generation: The LLM synthesizes a fluent, factually grounded answer based on that context.
🧠 Parametric vs Non-Parametric Memory
1
Parametric Knowledge (Inside LLM Weights): Information learned during training. Static, frozen in time, and completely unaware of your company's private documents.
2
Non-Parametric Knowledge (Outside in Storage): Your live PDFs, Word docs, Notion pages, and databases. Updated continuously without retraining.
💡 Analogy: Parametric memory is taking an exam from memory; RAG is taking an open-book exam with the exact relevant textbook pages open in front of you.
Section 2 RAG Fundamentals

Why Do We Need RAG?

Solving the 4 Critical Limitations of Pre-Trained Foundation Models

RAG MOTIVATION
1️⃣ Knowledge Cutoff Dates

LLMs stop learning on the day training finishes. A model trained in 2024 knows nothing about today's events, recent product releases, or policy changes updated this morning. RAG supplies real-time freshness instantly.

2️⃣ Private Proprietary Data

Public foundation models (GPT, Claude, Llama) have never seen your company's employee handbook, client contracts, private GitHub repos, or internal Jira boards. RAG connects LLMs to your private data securely.

3️⃣ Verifiable Citations

In business and healthcare, "trust me" doesn't work. RAG models can quote the exact document name, page number, and clause where an answer originated, allowing human users to instantly audit answers.

4️⃣ Zero Retraining Cost

When company policies change tomorrow, you don't spend $50,000 retraining an LLM. You simply upload the new PDF, replace the text chunk in storage, and the system immediately reflects the new policy.

What is Hallucination?

Understanding Why LLMs Invent Facts & How Context Grounding Prevents It

HALLUCINATION PREVENTION
🎭 Why Do LLMs Hallucinate?

An LLM is not a search engine or truth database; it is a probabilistic next-token predictor. It calculates: "Given this sequence of words, what is the most statistically plausible next word?"

  • • If the model lacks specific facts, it generates convincing, articulate fiction.
  • • It sounds authoritative, confident, and professional—yet is completely false!
  • • In medicine, finance, and legal workflows, hallucinations cause severe liability.
🛡️ How RAG Eliminates Hallucinations

RAG changes the task from creative writing from memory to reading comprehension. We bind the LLM with strict grounding instructions:

"You are an assistant. Answer the question ONLY using the facts in <context> below.
If the answer cannot be found in the context, respond strictly with:
'I do not have sufficient information in the provided documents to answer.'"
✓ The Grounding Guarantee: Grounded prompts force the model to anchor every claim in retrieved evidence.

RAG Architecture: Retrieval, Augmentation, Generation

The 3-Stage Pipeline Connecting User Inquiries to Grounded Responses

RAG ARCHITECTURE
Stage 1 1. Retrieval

The user's query is used to search the document database. The system retrieves the top-k most relevant text chunks containing pertinent facts.

Output: Top 3 text passages matching user query keywords or semantic meaning.
Stage 2 2. Augmentation

The application constructs an augmented prompt by stitching together system instructions, the retrieved document snippets, and the user's question.

Output: Prompt = Instructions + Context(Chunks) + Question
Stage 3 3. Generation

The augmented prompt is passed to the LLM (e.g. Groq / Llama). The model synthesizes the answer strictly based on the provided context with citations.

Output: Accurate, verifiable answer citing Section 4.2 of the Employee Handbook.

RAG Architecture: Document Processing vs Question Answering

The Crucial Distinction Between Ingestion Pipeline & Query Pipeline

DUAL-LIFECYCLE ARCHITECTURE
📥 1. Ingestion Pipeline (Offline / Background)

Runs ahead of time when documents are uploaded. Prepares raw files for fast search:

1
Load: Extract raw text from PDF, DOCX, TXT, or CSV.
2
Clean: Strip control characters, fix whitespace, normalize.
3
Chunk: Divide into 300-800 character pieces with overlap.
4
Tag: Attach metadata (docId, source, page, timestamp).
5
Index: Save into search index or vector store for lookup.
💬 2. Query Pipeline (Online / Live User Interaction)

Runs synchronously in real-time when a user asks a question in the app:

A
Receive Query: User submits question in UI.
B
Match Chunks: Query searches the pre-computed document chunks.
C
Augment Prompt: Inject top chunks into LLM prompt.
D
Generate: LLM produces final grounded answer with citations.

What is Document Processing?

The Crucial Pre-Processing Pipeline Converting Raw Files into LLM-Ready Knowledge

INGESTION FOUNDATION
📄 Why Can't We Just Upload Raw PDFs to LLMs?

A common beginner mistake is trying to dump a 150-page PDF directly into an LLM prompt. This causes severe production failures:

  • 💰 Skyrocketing Costs: Passing 100k tokens per prompt costs dollars per question!
  • ⏳ Unacceptable Latency: Multi-second delays while the model ingests massive token streams.
  • 🔍 "Lost in the Middle": Research proves LLMs struggle to recall facts buried deep in 100k+ token prompts.
  • 🧩 Raw File Artifacts: PDFs are binary layout streams containing font tables, page footers, and strange encoding artifacts.
⚙️ The 5 Stages of Document Processing
1
Extraction: Parse raw text out of PDF, Word (DOCX), CSV, and TXT files.
2
Cleaning: Remove control characters, normalize whitespace, clean page headers.
3
Splitting / Chunking: Divide text into semantic windows with overlap.
4
Metadata Attachment: Tag with source file, department, date, and page.
5
Storage: Export structured JSON ready for vector indexing.

Practical: Load PDF, TXT, DOCX and CSV

Building a Unified Document Loader Function in Node.js

PRACTICAL • DOC LOADER
documentLoader.js 
// documentLoader.js - Unified File Ingestion
const fs = require('fs');
const path = require('path');
const pdfParse = require('pdf-parse');
const mammoth = require('mammoth');
const { parse } = require('csv-parse/sync');

async function loadDocument(filePath) {
  const ext = path.extname(filePath).toLowerCase();
  const buffer = fs.readFileSync(filePath);

  switch (ext) {
    case '.txt':
    case '.md':
      return buffer.toString('utf-8');

    case '.pdf': {
      const data = await pdfParse(buffer);
      return data.text;
    }

    case '.docx': {
      const result = await mammoth.extractRawText({ buffer });
      return result.value;
    }

    case '.csv': {
      const records = parse(buffer, { columns: true, skip_empty_lines: true });
      // Convert rows into readable text representations
      return records.map(r => JSON.stringify(r)).join('\n');
    }

    default:
      throw new Error(`Unsupported file type: ${ext}`);
  }
}

module.exports = { loadDocument };
🔍 Architectural Highlights
  • 1. Single Entry Point: The rest of your application never needs to know whether the source was a Word document or a PDF. It simply calls loadDocument(path) and receives clean UTF-8 text.
  • 2. Buffer-Based: Loading via fs.readFileSync(filePath) works identically for both disk paths and multipart HTTP uploads.
  • 3. CSV Serialization: Tabular data is transformed into key-value JSON lines so LLMs can understand row column context during retrieval.
✓ Robustness: Throws clear descriptive errors for unsupported formats.

Document Cleaning

Purging Noise, Artifacts, and Irregularities from Extracted Text

TEXT SANITIZATION
documentCleaner.js 
// documentCleaner.js - Text Normalization
function cleanText(rawText) {
  if (!rawText) return '';

  return rawText
    // 1. Strip non-printable control characters (except \n and \t)
    .replace(/[\x00-\x08\x0B\x0C\x0E-\x1F\x7F]/g, '')
    // 2. Standardize carriage returns to standard newlines
    .replace(/\r\n|\r/g, '\n')
    // 3. Collapse multiple blank lines into at most 2 newlines
    .replace(/\n{3,}/g, '\n\n')
    // 4. Replace irregular tabs and multi-spaces with single space
    .replace(/[ \t]{2,}/g, ' ')
    // 5. Trim leading and trailing whitespace
    .trim();
}

module.exports = { cleanText };
🧹 Why Cleaning is Non-Negotiable

Raw text extracted from PDFs often contains garbage characters, null bytes, and 50 consecutive newlines.

Before (Raw PDF Text):
"Employee      Leave\x00Policy\r\n\r\n\r\n\r\nSection  4.2"
After (Clean Text):
"Employee Leave Policy\n\nSection 4.2"
💎 Token Savings: Cleaning eliminates up to 25% of wasted whitespace tokens before chunking!
Section 3 Document Processing for RAG

Text Splitting / Chunking

Why Splitting Long Documents into Manageable Units is Mandatory

CHUNKING THEORY
✂️ What is Text Chunking?

Text Chunking is the process of breaking a continuous text document into smaller, coherent, standalone text segments called chunks.

1
Laser-Focused Search: Instead of searching an entire 50-page manual, the search engine matches the single 300-character paragraph that answers the question.
2
Prompt Budget Fit: Chunks fit cleanly within the prompt alongside system instructions, history, and the user's question.
3
Prevents Semantic Dilution: An embedding of an entire book averages out and matches nothing well; an embedding of one paragraph is razor sharp.
⚖️ The Granularity Trade-Off
Too Small
Chunks < 100 characters: Loses context. The chunk might say "it was approved on Tuesday" without indicating what "it" refers to!
Too Large
Chunks > 2,000 characters: Dilutes key details and fills up context limits with irrelevant filler text.
Optimal
Sweet Spot: 300 – 800 characters (roughly 75 – 200 words). Highly focused and semantically coherent.
Section 3 Document Processing for RAG

Chunk Size and Chunk Overlap

Preserving Semantic Continuity Across Split Boundaries

OVERLAP MECHANISM
🔄 The Critical Problem of Hard Boundaries

If you split text strictly every 500 characters, sentences get sliced in half! A vital rule like: "The server password can be reset by..." might get cut so that the actual procedure ends up in the next chunk, making both chunks useless.

Sliding Window with Overlap Visualizer:
Chunk 1: [Chars 0 → 400] "...medical insurance covers 100% of dental procedures subject to annual deductible"
Chunk 2: [Chars 350 → 750] "subject to annual deductible of $250 per dependent when enrolled prior to..."
📐 Recommended Ratios

Standard industry practice recommends an overlap of 10% to 20% of the chunk size.

  • • Chunk Size: 500 chars → Overlap: 50-75 chars.
  • • Chunk Size: 1000 chars → Overlap: 100-150 chars.
💡 The Step Size Formula

In a sliding window algorithm, the window advances by:

step = chunkSize - overlap

function splitText(text, chunkSize = 300, overlap = 50) { if (!text) return []; const chunks = []; const step = chunkSize - overlap; let start = 0; while (start < text.length) { const end = Math.min(start + chunkSize, text.length); const chunk = text.substring(start, end).trim(); if (chunk) chunks.push(chunk); if (end >= text.length) break; start += step; } return chunks; } module.exports = { splitText };
